# Auditoria de dívida técnica — My Daily Pet

Data: 2026-08-13
Estado do repositório: `main` = `develop` = `df93e02` (targetSdk 36, versionCode 25)

Boa parte do que está aqui foi descoberto durante a migração para `targetSdk 36`,
não por inspeção teórica: cada item abaixo ou custou tempo naquela migração, ou
esteve a um passo de causar um incidente.

## Método de priorização

`Prioridade = (Impacto + Risco) × (6 − Esforço)`, cada eixo de 1 a 5.
Esforço entra invertido: consertos baratos sobem.

- **Impacto** — quanto atrasa o desenvolvimento hoje
- **Risco** — o que acontece se ficar como está
- **Esforço** — dificuldade do conserto

## Justificativa por item

### 1. Deploy publica direto em produção, sem rollout — **35**

`fastlane/Fastfile`, lane `deploy`, chama `upload_to_play_store` sem `track:`.
O default do `supply` é `production`. Confirmado no log de 2026-08-13:
`track | production`, `release_status | completed`, sem `rollout`.

Uma tag `v*` publica para 100% dos usuários de uma vez. No deploy da v1.3.0,
o que impediu isso foi um acidente — colisão de `versionCode` — e não um
controle.

**Negócio:** um crash de regressão atinge toda a base antes de qualquer sinal.
Sem rollout, não há como pausar; só resta subir uma nova versão e esperar a
adoção.

**Conserto:** uma linha — `upload_to_play_store(track: 'internal')` ou
`(track: 'production', rollout: '0.05')`.

> Já oferecido duas vezes e recusado nas duas. Fica registrado como decisão
> consciente, não como esquecimento.

### 2. Processo de release é conhecimento tribal — **30**

Não existe runbook. O repositório não tem `CLAUDE.md` nem documento de release.
Isso já custou um deploy falho: o `versionCode` foi deduzido do `build.gradle`
da `develop`, que desconhecia os códigos consumidos pela branch
`hotfix/fix_crash_in_app_update`.

**Negócio:** cada release depende de quem lembra dos detalhes. O erro de
`versionCode` vai se repetir.

**Conserto:** um `docs/RELEASE.md` com a sequência real (versão vem do Play
Console, não do repo; tag dispara produção; secrets no CI) — meia hora.

### 3. Sete vulnerabilidades abertas no Dependabot — **28**

3 altas, 3 moderadas, 1 baixa, reportadas em todo push. Não consegui listar
quais pacotes (sem `gh` CLI nesta máquina) — **o primeiro passo é abrir o painel
e classificar**, não presumir.

Dado que Firebase BOM e Compose BOM estão parados desde 2023/2024, é provável
que boa parte se resolva com os itens 8 e 16.

**Negócio:** vulnerabilidade conhecida em app publicado é exposição direta.

### 4. CI não roda em pull request — **35**

`.github/workflows/android.yml` declara `push` para `main` e, desde
`c20b703`, `workflow_dispatch`. Não há gatilho de `pull_request`.

Consequência vivida: durante toda a migração de `targetSdk`, `bundleRelease`,
R8 e `lintVitalRelease` nunca rodaram — o primeiro build de release só existiu
quando a tag foi empurrada, já em produção.

**Negócio:** todo PR é revisado sem sinal de build. Erros de release aparecem
no pior momento possível.

**Conserto:** adicionar `pull_request: branches: [main, develop]`. Funciona
para branches do próprio repositório, que é o caso.

### 5. Nada é executado em dispositivo no pipeline — **24**

Nem emulador, nem Firebase Test Lab, nem Gradle Managed Devices. A migração
para Android 16 foi publicada sem que uma única tela fosse aberta.

**Negócio:** mudanças de plataforma — edge-to-edge, orientação, insets — só
falham em runtime. Nenhuma delas é detectável por compilação ou lint.

**Conserto:** Gradle Managed Devices no CI dá um smoke test sem infraestrutura
externa. Começar com um teste que abre a Home e verifica que ela renderiza.

### 6. Branches divergem sem reconciliação — **24**

`hotfix/fix_crash_in_app_update` (nov/2025) tem `versionCode 21` e nunca foi
mesclada. Releases saíram dela, e nem `main` nem `develop` registraram isso.
Foi a causa raiz do deploy falho da v1.3.0.

**Negócio:** o repositório deixa de ser fonte de verdade sobre o que está
publicado.

**Conserto:** mesclar ou apagar a branch órfã, e decidir se hotfixes voltam
para `develop` por política.

### 7. `RECEIVE_BOOT_COMPLETED` sem receiver — **24**

A permissão está declarada em `AndroidManifest.xml:26`, mas não existe nenhum
receiver de `BOOT_COMPLETED` em módulo nenhum. Os alarmes agendados via
`AndroidAlarmScheduler` usam `setExactAndAllowWhileIdle`, que **não sobrevive a
reboot**.

**Negócio:** este é um app de lembretes. Reiniciar o telefone apaga
silenciosamente todos os lembretes do usuário — que só descobre quando o
lembrete não chega. É o bug mais danoso desta lista para o produto.

**Conserto:** um `BootReceiver` que reagenda a partir do banco. Meio dia.

### 8. Firebase BOM 32.2.0 — **21**

Julho de 2023, três anos. Arrasta Crashlytics e Analytics junto.

### 9. CI nunca roda os testes de instrumentação — **21**

Existem **10 arquivos** em `androidTest/`. Nenhum workflow chama
`connectedAndroidTest` ou equivalente. São testes escritos, mantidos no
repositório, e nunca executados.

**Negócio:** custo de manutenção sem nenhum retorno. Provavelmente já não passam.

### 10. `jacocoTestReport` quebrado — **20**

`app/build.gradle:229` usa `dependsOn['testDebugUnitTest', 'createDebugCoverageReport']`.
Groovy lê `x[a, b]` como `x.getAt([a, b])` — leitura de índice, não declaração
de dependência. A task quebra ao ser realizada, o que também derruba
`./gradlew :app:tasks`.

**Conserto:** trocar por `dependsOn('testDebugUnitTest', 'createDebugCoverageReport')`.
Um caractere de diferença, e destrava a medição de cobertura.

### 11. `datastore-preferences` 1.0.0 — **20**

De 2021. Cinco anos sem atualizar, guardando preferências do usuário.

### 12. `versionCode` quebra se a env var for definida — **20**

`versionCode System.getenv("VERSION_CODE") ?: 25` — `getenv` devolve `String`,
o AGP exige `Integer`. Funciona hoje só porque nada define a variável. É uma
armadilha para quem tentar parametrizar a versão no CI.

**Conserto:** `(System.getenv("VERSION_CODE") ?: "25").toInteger()`.

### 13. `targetSdk` em 12 módulos library — **20**

Não tem efeito em módulos library, é deprecado desde o AGP 8.1 e **removido no
AGP 9.0**. Como as versões agora estão centralizadas no version catalog, apagar
é trivial.

### 14. Insets: `CONSUMED` na raiz, sem `ime()` — **20**

`MainActivity.kt` consome todos os insets na raiz, então nenhum fragment
consegue reagir a insets — inclusive os do teclado. Com edge-to-edge,
`adjustResize` não redimensiona mais a janela, o que expõe campos de texto
ancorados na base dos formulários de pet, lembretes e tarefas.

### 15. 12 de 13 módulos sem nenhum teste — **18**

**28 arquivos de teste no projeto inteiro, todos em `app`** (18 unitários, 10 de
instrumentação), contra 159 arquivos de produção. Os módulos `core`, `data`,
`pet_*`, `reminder_*`, `tasks_*` e `settings_*` — onde vive a lógica de domínio
e o acesso a banco — têm cobertura zero.

**Negócio:** é o maior multiplicador de risco da lista. Todo item de refatoração
aqui fica mais caro e mais arriscado porque não há rede.

**Conserto:** não é um esforço único. Ver plano de fases.

### 16. Compose BOM 2024.10 / Material 1.11 — **18**

Ambos com quase dois anos.

### 17. AdMob 22.2.0, nunca executado em API 36 — **18**

Julho/2023. A decisão de mantê-lo na migração foi correta — não há requisito de
16 KB, e subir exigiria bump de Kotlin — mas ele foi publicado em `targetSdk 36`
tendo sido apenas **compilado**, nunca executado nessa API.

**Bloqueado pelo item 20.**

### 18. `USE_EXACT_ALARM` sem justificativa — **18**

A política do Play reserva essa permissão a apps cuja função central é
despertador ou calendário. Um app de lembretes de pet é discutível. Passou nas
revisões até aqui, mas é o candidato mais provável a rejeição futura.

**Conserto:** remover, manter só `SCHEDULE_EXACT_ALARM`, checar
`canScheduleExactAlarms()` e cair para alarme inexato.

### 19. `FOREGROUND_SERVICE` e intent-filter mortos — **19**

`FOREGROUND_SERVICE` declarado sem nenhum `<service>` no projeto — dispara
prompt de declaração no Play Console à toa. E o `NotificationReceiver` tem um
`<intent-filter>` com `<category>` e nenhuma `<action>`, que nunca casa com nada.

### 20. Kotlin 2.0.0 bloqueia bibliotecas novas — **14**

Já custou concretamente: `play-services-ads` 25.4.0 traz metadata de Kotlin
2.3.0 e o `:app:kspDebugKotlin` falha com 19 erros. Kotlin, KSP e o plugin do
Compose são acoplados pela mesma chave do catalog, então é um upgrade só.

**É o desbloqueador dos itens 16 e 17.** Esforço alto porque toca Hilt, Room e
Compose de uma vez — e o item 15 significa que não há testes para segurar.

### 21. `kapt` em 12 módulos — **10**

Todo build imprime `Kapt currently doesn't support language version 2.0+.
Falling back to 1.9`. Gera stubs Java e roda o compilador duas vezes. O projeto
já usa KSP em paralelo; o `kapt` restante é do Hilt.

**Negócio:** puro tempo de build, em toda compilação, para todo mundo.

### 22. `bitbucket-pipelines.yml` órfão — **10**

Aponta para `androidsdk/android-30` e duplica o que o GitHub Actions faz. Se
ninguém usa Bitbucket, é documentação enganosa.

## Plano de remediação por fases

Cada fase cabe ao lado de trabalho de feature. Nenhuma exige congelar o roadmap.

### Fase 0 — Meia hora, faça antes do próximo release

Todos são de uma linha, sem risco, e vários já mordem hoje.

| Item | Ação |
|---|---|
| 10 | `dependsOn(...)` em `app/build.gradle:229` — destrava `:app:tasks` e a cobertura |
| 12 | `.toInteger()` no `versionCode` |
| 19 | Apagar `FOREGROUND_SERVICE` e o `<intent-filter>` vazio |
| 22 | Apagar `bitbucket-pipelines.yml`, se Bitbucket não é usado |
| 4 | Adicionar gatilho `pull_request` ao `android.yml` |

### Fase 1 — Semana 1: segurança do release

O objetivo é parar de publicar às cegas.

1. **Item 3** — abrir o painel do Dependabot, classificar as 7 e corrigir as 3 altas.
2. **Item 2** — escrever `docs/RELEASE.md`. O `versionCode` vem do Play Console.
3. **Item 6** — resolver a branch `hotfix/fix_crash_in_app_update`: mesclar ou apagar.
4. **Item 7** — `BootReceiver` que reagenda os alarmes. É o pior bug de produto aqui.
5. **Item 1** — decidir conscientemente sobre `rollout`, mesmo que a decisão seja manter.

### Fase 2 — Semanas 2 a 6: dependências, na ordem certa

A ordem importa, porque uma destrava as outras.

1. **Item 13** — remover `targetSdk` dos módulos library. Preparo barato para o AGP 9.
2. **Item 15, parcial** — antes de mexer em dependência, escrever testes para `core` e `data`. Não é cobertura completa: é a rede mínima para o passo seguinte.
3. **Item 20** — subir Kotlin, KSP e o plugin do Compose juntos. **Nada mais nesta fase começa antes disto.**
4. **Itens 8, 11, 16, 17** — Firebase, DataStore, Compose/Material e AdMob. Um por vez, cada um com seu build verde.
5. **Item 21** — com o Kotlin novo, migrar o `kapt` restante do Hilt para KSP.

### Fase 3 — Contínuo: testes e verificação

Sem prazo fechado; é mudança de hábito, não projeto.

- **Item 15** — regra: todo módulo tocado ganha teste antes da mudança. Prioridade para `data` (banco) e `*_domain` (use cases).
- **Item 9** — fazer os 10 testes de instrumentação passarem, ou apagá-los. Manter teste que nunca roda é pior que não ter.
- **Item 5** — Gradle Managed Devices no CI, começando por um smoke test da Home.
- **Items 14, 18** — insets e `USE_EXACT_ALARM`, quando houver teste em dispositivo para validar.

---

## O que esta lista não cobre

- **Quais são as 7 vulnerabilidades.** Sem `gh` CLI nesta máquina, não consegui listar. É o primeiro passo da Fase 1, não um palpite.
- **Cobertura de teste real em porcentagem.** O `jacocoTestReport` está quebrado (item 10), então só sei a contagem de arquivos, não a cobertura. Depois da Fase 0 dá para medir.
- **Dívida de arquitetura.** Não encontrei nenhuma relevante: os 13 módulos têm fronteiras claras, e o maior arquivo tem 352 linhas. A estrutura do projeto é o ponto forte dele.
